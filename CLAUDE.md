# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**upgrade-gitlab** is an automated, Docker-based GitLab upgrade tool that performs safe, step-by-step version upgrades following the official GitLab upgrade path. Single bash script (`upgrade-gitlab`, ~2150 lines) supporting CE/EE editions with background migration tracking, stuck-migration detection, signal safety, and Discord notifications.

Repository: `gitlab.gggames.synology.me/peter/gitlab/upgrade-gitlab` (GitLab, not GitHub — use `glab` instead of `gh`). The former `gitlab.com/gitlab-useful-scripts/upgrade-gitlab` is being retired; its CI can no longer create jobs (GitLab.com requires account identity verification).

## Architecture

### Single-Script Design
The entire tool is one bash script (`upgrade-gitlab`) with no external library dependencies beyond standard CLI tools (docker, curl, jq, sort, bash 4.0+).

### Upgrade Path Resolution
Single unified source: **path.json** provides required waypoints (major.minor stops), **Docker Hub** resolves each waypoint to its latest patch version and determines the overall latest tag. No `--source` flag, no freshness check, no interactive prompt.

### Signal Safety
The whole post-confirmation flow (after pre-upgrade secrets check, through runner-resume) runs as a single `enter_critical`/`exit_critical` zone. Inside that zone, SIGINT/SIGTERM/SIGTSTP/SIGHUP set the `_interrupted` flag and return without exiting. Each upgrade-loop iteration begins with a flag check that breaks the loop early when set; post-upgrade verification (health, secrets, runner resume) then still runs, after which the script exits 130. The recovery branch (line 1782) opens its own short-lived critical zone with the same semantics. Ctrl+\\ (SIGQUIT) forces immediate exit at any time. `check_gitlab_server_healthy` no longer manages its own critical zone — it relies on the caller's outer zone.

### Stuck Migration Detection
`_check_stuck_migrations` runs at the top of every `wait_for_background_migrations` call and scans `batched_background_migrations` for rows with `updated_at` older than 7 days. Routing by status:
- `failed(4)` → FATAL banner + recovery guide + `exit 1` (always; auto recovery is unsafe).
- `finalizing(5)` → FATAL in `-y` mode; interactive mode polls every 30s until resolved externally; `--reset-stuck-finalizing` auto-resets to `active(1)` so GitLab re-finalizes on the next post-deploy migration (does NOT run the finalize rake itself).
- `paused(0)`/`active(1)`/`aborted(2)` stale → warning only (may be a slow active migration).

### Main Upgrade Flow
1. Pre-flight checks (disk space, secrets integrity)
2. Backup (gitlab-backup or gitlab-rake for <12.2)
3. Version upgrade loop: for each stop → pre-pull next image → wait for background migrations → swap container → health check → verify migrations. An edition switch (CE→EE) is the loop's first stop: its same-version tag is prepended to `UPGRADE_POINTS_ARRAY`, and only the messages differ (`ver == EDITION_SWITCH_TAG`). It used to run in a block of its own before the loop, which then removed the tag from the array and overwrote `CURRENT_VERSION` — the mutation behind #21 (#27). Now `CURRENT_VERSION` and `UPGRADE_POINTS_ARRAY` stay the start version and the whole route for the entire run; the version running now is `CNT_VERSION` alone. The image to remove after a swap is derived from that tag (`_official_image_for_tag`), whose edition suffix is the old edition on a switch hop.
All `docker stop` calls pass `-t $STOP_TIMEOUT` (300s). The 10s default SIGKILLs GitLab — a real shutdown measures 32-55s — leaving PostgreSQL/Gitaly to crash-recover on the next boot. `-t` is a ceiling, not a fixed wait, so a generous value costs nothing when shutdown is clean.
4. Post-upgrade: final health check, resume paused runners

### Recovery Path
When `UPGRADE_POINTS_ARRAY` is empty (already at target) AND `_prev_exit != 0` (previous container exit was abnormal), the script skips backup and re-runs health/migration/secrets checks only. `docker kill` sets ExitCode=137, so an invocation following a killed container enters this path without taking a fresh backup — the handle used to reach it manually when reproducing stuck-migration scenarios against a real PostgreSQL.

### Backup Progress Tracking
A background `_size_poller` runs `docker exec` in a loop and writes per-tick lines to a tempfile: sizes of `*.tar.gz` staging files, size of the assembled `*_gitlab_backup.tar`, and total non-loopback `tx_bytes` from `/sys/class/net/*/statistics`. `run_with_progress_bar` consumes these to compute per-stage percentages:
Stages pass an `approx` flag to `_draw_backup_progress`; when set, the percentage renders as `~N%` and `_backup_progress_extra` renders the ETA as `ETA ~HH:MM:SS`. Every `*.tar.gz` stage is approximate by construction: the numerator is the gzipped file (`Backup::Helper#compress_cmd` is `gzip -c -1`, overridable via `COMPRESS_CMD`) while the denominator is the uncompressed byte count from the DB, so the bar reads low by the compression ratio. Count-based and raw-byte-based stages (`Dumping repositories`, `Creating backup archive`) are exact and must not gain a `~`.

- `Dumping repositories` → `_total_project_count` vs `"completed create"` log lines (exact)
- `Dumping uploads/artifacts` → `~` tar.gz size vs precomputed total from `project_statistics`. These carry the same object-storage overcount as lfs did, but deliberately keep the `project_statistics` denominator: the precise source (`ci_job_artifacts`) is renamed to the partitioned `p_ci_job_artifacts` in newer schemas, and `_query_backup_stats` runs against the *pre-upgrade* version, so the table name is not stable across the range this tool traverses. Both stages are a ~1% sliver of backup wall-clock; a silently-failing fallback is not worth it.
- `Dumping builds` → indeterminate. `builds.tar.gz` holds CI job logs (`Settings.gitlab_ci.builds_path`), a different tree from `artifacts.tar.gz` (`JobArtifactUploader.root`), and no size column tracks it. Do not fold it back into the artifacts branch — doing so measures a file that does not exist yet at that point in the backup.
- `Dumping lfs objects` → `~` `lfs.tar.gz` size vs `SUM(size) FROM lfs_objects WHERE COALESCE(file_store,1)=1` (`_query_lfs_disk_size`). `lfs.tar.gz` archives the oid-addressed *deduplicated* store, so `SUM(project_statistics.lfs_objects_size)` is the wrong denominator twice over: it double-counts objects shared across forks, and it counts objects that live in object storage and never reach the tar. The query falls back to the `project_statistics` value on failure (old GitLab, permissions); a legitimate `0` is a success and correctly yields an indeterminate bar.
- `Creating backup archive` → assembled tar size vs the staging total. GitLab's `pack` only deletes staging content in its `ensure` block (after the tar is written and uploaded), so the denominator stays valid for the whole stage. The total comes from a one-shot `du -sb --exclude=*_gitlab_backup.tar` fired asynchronously on stage entry (`_start_pack_total_probe`) — `du` can take seconds on a large staging dir, so the bar stays indeterminate until the value lands, and stays indeterminate for good if the probe fails.
- `Uploading backup archive to remote storage` → egress bytes since stage start vs final tar size, rendered with `~` prefix to indicate approximation (fog SDK's per-chunk open/close defeats FD-position tracking, so network bytes are the only viable signal)

### Config Backup Lifecycle
After GitLab's `.tar` backup (which GitLab handles + uploads itself if `backup_upload_*` is configured), the script:
1. Archives the whole `/etc/gitlab` volume with `gitlab-ctl backup-etc` (#26). It replaced separate copies of `gitlab.rb` and `gitlab-secrets.json` in `BACKUP_DIR`: those duplicated the archive and put the decryption key next to the app backup tar, undoing the separation below. A hook from the earlier template that `docker cp`s the two copies now fails (warning only) and uploads nothing; README tells users to switch it to the archive. GitLab's app backup leaves that volume out on purpose, and in the Docker image it holds far more than the two files: the SSH host keys (`docker/assets/sshd_config` points `HostKey` at `/etc/gitlab/ssh_host_*`), `ssl/`, `trusted-certs/`, the Gitaly commit signing key, the license file. Picking files one by one is what missed the signing key; the whole volume follows whatever is added later. `backup-etc` writes `/etc/gitlab/config_backup/gitlab_config_<epoch>_<date>.tar`, mode 600 in a 700 directory, excluding its own directory; that location is a different volume from `BACKUP_DIR`, in line with the official advice not to keep an encrypted database next to its key. On versions without `backup-etc` (or when it fails) `_CONFIG_BACKUP_SH` runs the same `tar` with the same name. The archive path is taken from the newest file in the directory, not from `backup-etc`'s output text, which is not guaranteed across versions. A failed archive aborts the run before the critical zone, like a failed app backup: without `gitlab-secrets.json` the app backup cannot be restored. It runs through `_run_isolated`, so a Ctrl+C waits for the archive and then exits 130 through the EXIT trap.
2. Prunes old archives, and copies left by earlier runs, using `gitlab.rb`'s `backup_keep_time` (parsed with the same simple grep+awk+sed pattern as `backup_path`; missing/0 = keep forever, mirroring GitLab's own retention semantics for `.tar`). `backup-etc` prunes its archives by the same value from the node attributes; the script's own pass also covers the `tar` fallback.
3. Optionally invokes a user hook (see `UPGRADE_GITLAB_CONFIG_HOOK` below). The hook receives the container-side `UPGRADE_GITLAB_CONFIG_ARCHIVE` and `BACKUP_DIR` (host-path translation is intentionally left to the hook via `docker cp`, so the feature works regardless of mount topology). Hook failures warn but never abort the upgrade.

Not covered yet (the rest of #26): files outside `/etc/gitlab` that `gitlab.rb` points to (`from_file`, certificate paths), encrypted settings and global server hooks under `/var/opt/gitlab`, file hooks inside the image (lost on every hop), and the container definition itself.

### Image Hook (Patched Images)

Some instances run the official image plus local source patches (#20; the patches themselves live in `peter/gitlab/gitlab-patches`). Omnibus ships the Rails sources as plain files, so a patched image is `FROM gitlab/gitlab-<ed>:<ver>` + `git apply`. Without support, such a container is either not detected at all, or, if also tagged as the official image, every hop starts the official image and the patches vanish while the upgrade still reports success.

`UPGRADE_GITLAB_IMAGE_HOOK` (or an executable `build-image.hook` next to the script) builds the image for each hop. Discovery shares `_find_hook` with the config hook; everything after discovery deliberately differs:

- **Contract**: the hook gets `UPGRADE_GITLAB_BASE_IMAGE` and prints the image to run as the last stdout line. `_prepare_run_image` then requires `_official_image_of` to resolve the result as a *derived* image of exactly that base, via the `org.upgrade-gitlab.base` label (`_BASE_LABEL`). A hook that returns the official image or another version would otherwise start an unpatched container without a word.
- **Timing**: `_prepare_run_image` runs at the top of each hop (the CE→EE switch included), before the old container is stopped. It pulls the official image, runs the hook if configured, and creates the replacement container under a temporary name (see Container Recreate), so the swap itself (`_swap_container`) is only stop → rm → rename → start. This applies without a hook too: the pull used to happen after `docker rm`, where a failed pull left no container at all.
- **Failure**: a failed pull, hook or container create sets `_image_prep_failed` and breaks the loop like an interrupt, so post-upgrade verification and `_release_upgrade_holds` still run, then exits 1 with the current version still up. A plain `exit` inside the critical zone would skip the hold release, since the EXIT trap leaves holds alone while `_trap_active=1`. A configured-but-not-executable hook is fatal, not a warning as for the config hook.
- **Detection**: `_official_image_of` is the one place that maps an image to its official image: the name itself, then the base label, then RepoTags (one `docker image inspect` reads both). The label wins over RepoTags, because a derived image that was also tagged official must still be treated as derived. Container detection, edition detection and the hook-result check all use it. A derived container with no hook configured would lose its patches, so before the backup an interactive run asks (y/N, default no; dropping patches on purpose is legitimate) and `-y` refuses, since unattended this state is most likely a lost hook symlink. `--dry-run` only warns.
- **Isolation**: the hook runs through `_run_isolated`, the core that `_exec_isolated` also uses, so a Ctrl+C in the critical zone does not kill a half-done build and turn an interrupt into a hook failure. Its stderr lands in `_exec_err` and is shown (last 20 lines, `_print_exec_err_tail`) only on failure.
- **Cleanup**: `_remove_previous_image` removes `RUNNING_IMAGE` together with the previous official image. `RUNNING_IMAGE` starts out set only for a derived container, so a first hop from an official image run under another name (`:latest`, a RepoTags alias) leaves that tag alone, as before; after each swap it is the image the script started.

### Object Storage Detection

`_detect_object_storage_skips` backs `--skip-object-storage`. It reads the **runtime** `Gitlab.config`, not gitlab.rb and not the rendered gitlab.yml. This is not a stylistic choice: consolidated object storage (`gitlab_rails['object_store']['enabled']` + `['objects'][type]['bucket']`) is merged into each type's section by `config/object_store_settings.rb` at Rails boot, *after* omnibus has written gitlab.yml. The rendered yml still shows `<type>.object_store.enabled: false`; only the booted config reflects the truth. Reading runtime config is therefore the one approach that handles the legacy per-type flags (`gitlab_rails['artifacts_object_store_enabled']`) and the consolidated form identically, with no branching.

Detection requires `enabled` **and** a non-empty `remote_directory`. `enabled` alone is not sufficient: `object_store_settings.rb` only raises on a missing bucket when the *type* section's own `enabled` is truthy (`missing_bucket_for`), so a type whose section leaves `enabled:` blank — `agent_plan_content`, `ci_secure_files` — ends up with `object_store.enabled = true` and no bucket. That state means the data is still on disk, and skipping it would drop it from the backup without it existing anywhere else. Observed on a real 19.2.5 instance: every configured type reported `remote_directory="<bucket>"`, `agent_plan_content` reported `nil`. The merge moves `bucket` into `remote_directory` and deletes the original key (`split_bucket_prefix`), so `remote_directory` is the only name visible at runtime. In the legacy path omnibus always renders a `remote_directory` default, so the extra condition filters nothing there.

`_OBJECT_STORAGE_TYPES` holds the type list in one place — the Ruby snippet and the output whitelist both derive from it, since a list duplicated across the two drifts silently. Membership is decided by *backup targets*, not by object storage support: a name only belongs there if `lib/backup/tasks/` has a matching `self.id`, because the result becomes `SKIP=`. `dependency_proxy` supports consolidated object storage but has no backup task, so it is deliberately excluded; `agent_plan_content` has both, so it is included. Backup target ids as of 19.2.5: `agent_plan_content artifacts builds ci_secure_files db external_diffs lfs packages pages registry repositories terraform_state uploads`.

### Maintenance Mode

Enabled by default right before the backup, disabled at the end; `--no-maintenance-mode` opts out. The purpose is backup consistency: no non-admin writes between the DB dump and the repository dumps.

Availability is decided inside `gitlab-rails runner` (`_MAINTENANCE_ENABLE_RUBY`), never from the DB. On a real 19.2 EE instance `License.current&.plan` was `nil` while `License.feature_available?(:maintenance_mode)` was `true` and the Admin UI section was present, so a DB-side license check would give the wrong answer. CE (`License` undefined) and pre-13.9 schemas (no column) both surface as `NameError` → `unavailable`; any other exception → `error`. Neither blocks the upgrade.

Writes go through `ApplicationSetting.current_without_cache.update!`, not psql: an SQL `UPDATE` leaves the settings cache (process memory + Redis) stale.

When `--skip-object-storage` is also set, both snippets run in one rails boot; `_detect_object_storage_skips` filters runner output from stdin with the type whitelist, which is what keeps the `maintenance_mode=` line out of `SKIP=`.

Release goes through `_release_upgrade_holds`, which resumes paused runners, disables maintenance mode and restores the restart policy (see Container Recreate) together — every exit path (normal end, recovery, already-satisfied, EXIT trap) calls that one function, so a further hold does not have to be threaded through four call sites again. All three are idempotent: `_resume_paused_runners` clears `PAUSED_RUNNER_IDS` after a successful resume so a second call cannot re-resume from the memory fallback.

A persistent `.maintenance-mode` state file next to the runner state file is the source of truth, it is removed only after a successful disable, and a leftover file is released by the next run. `already` (the admin turned it on) writes no state file, so it is never turned off by the script. A failed disable is not retried inside the same process (`_maintenance_release_attempted`): the state file already carries the retry to the next run, and a rails boot costs around 5 minutes per attempt (measured on 19.2.6: 2m22s CE, 3m52s EE; a larger or busier instance takes longer), unlike the sub-second psql UPDATE behind runner resume. That cost is also why the enable snippet shares the pre-backup boot with `--skip-object-storage` rather than taking its own, and why the feature adds roughly ten minutes per run in total (one boot before the backup, one to release at the end) — accepted because a real upgrade spends far longer in backup and hops. The EXIT trap skips the whole release under `--dry-run` — that flag promises to compute the path and change nothing, including holds left by another run.

Every `gitlab-rails runner` call goes through `_rails_runner` (a thin wrapper over `_exec_isolated`, itself `_run_isolated` around `docker exec`, which serves any side-effecting `docker exec` whose result the script needs; stdout lands in `_exec_out`, stderr in `_exec_err`), because a terminal Ctrl+C signals the whole foreground process group: it kills the `docker exec` client, but the runner inside the container carries on regardless (reproduced on docker 29.8 — the in-container side effect happened while the client returned empty output). Pressed during the enable boot, that meant the script exited without the `enabled` result and so without a state file, and minutes later the orphaned runner turned maintenance mode on with nothing left to turn it off. `_rails_runner` starts the client under `set -m` so it gets its own process group and the terminal's signal never reaches it (pure bash — `setsid` is not guaranteed on DSM), and defers signals like a critical zone while it waits via `_wait_reap`. The caller acts on the deferred `_interrupted` only after the result is recorded; before the backup that is an `exit 130`, which the EXIT trap turns into a proper release. Results come back through the `_exec_out` global rather than command substitution, since traps revert to their defaults inside a `$(...)` subshell and the deferral would silently stop working. The cost is that Ctrl+C now waits out the in-flight boot — the container was going to run it to completion either way. Ctrl+\\ (SIGQUIT) still forces an immediate exit, and with it the old orphan risk.

### Running CI Jobs

Pausing the runners only stops new jobs from being picked up; a job that is already running keeps writing through the backup and the container swaps (#17). The script never cancels a job, because the job may be a deployment. Once the runners are paused it recounts running jobs and either waits for them (`--running-jobs=wait`, the default) or aborts the upgrade without touching them (`--running-jobs=abort`). Interactive runs ask `[w]ait / [a]bort`, with the flag value as the default. `--running-jobs-timeout` bounds the wait; `0`, the default, waits indefinitely, and when the timeout is exceeded the run aborts rather than switching to cancelling. The abort happens before the critical zone, so the EXIT trap resumes the runners. It is reported as `WARN`, not `ERR`, because it is a deliberate skip.

The decision must be made before maintenance mode is enabled. Once it is on, a job that finishes still shows `running` (per the GitLab docs), so a wait started afterwards would never end.

The count is psql-only, so it needs no rails boot. On 19.2.6 there is no `ci_builds` table at all: only the partitioned parent `p_ci_builds` exists, with rows in `gitlab_partitions_dynamic.ci_builds_NNN`. Older versions have only `ci_builds`. The query therefore uses `COALESCE(to_regclass('p_ci_builds'), to_regclass('ci_builds'))`, since the partitioned parent, where it exists, always covers everything. `canceling` counts as running, because the runner is still finishing the job (running `after_script`); on versions without that state, it simply matches nothing. The listing shown on the confirmation screen takes the project path from `routes` and the pipeline id straight from `commit_id`, so no pipeline-table join is needed (that table is partitioned as `p_ci_pipelines` on 19.2.6).

### Backup Failure and Cancellation

Two failure modes combined into "an irreversible upgrade with no backup of the current version" (#16), and both are now closed.

**A failed backup aborts.** The backup's exit code used to be ignored, so a failure went straight on to config copies, the critical zone and the container swap. Upstream (checked at `v19.2.6-ee`): `Backup::Manager#create` returns `create_task_result.all?` and the task does `exit 1 unless success`; DB/file-target errors (`DatabaseBackupError`/`FileBackupError`) are logged and the remaining targets still run, while a repository failure raises plain `Backup::Error` and aborts at once. Either way the code is non-zero, and nothing exits non-zero on a mere warning, so non-zero means incomplete. It always aborts, interactive or not. Unlike the pre-upgrade secrets check there is deliberately no "continue anyway" prompt: this tool cannot roll back, and an incomplete backup is not a backup. The way forward is to fix the cause, or to exclude a target explicitly with `--skip-*`.

**Cancelling a backup stops the one inside the container.** The client dies on Ctrl+C but `gitlab-backup` does not, and it would carry on through `pack` → `upload` → `remove_old` after the holds were released. Worse, 16.0+ serializes backups through `Rails.root/tmp/backup_restore.pid` (`lock_backup`, MR !119004), so re-running right away failed the new backup on the lock, and that failure used to be ignored. `_backup_in_progress` brackets the backup call, and the EXIT trap calls `_stop_container_backup` *before* `_release_upgrade_holds` — releasing maintenance mode while the dump is still running would defeat it. The stop sends SIGTERM, not SIGKILL: the backup code has no signal handling, so Ruby raises `SignalException` and the `ensure` blocks clean staging and delete the PID file. The target is `pgrep -f "$_BACKUP_PROC_PATTERN"` (`gitlab[:]backup[:]create`), which matches the rake ruby process and not the `gitlab-backup create` bash wrapper, and covers the <12.2 `gitlab-rake` path too. The pattern is defined once because it is used in three places: the first liveness check, the in-container wait, and the size poller. The bracket form matches the real process but not an `sh` loop that carries the pattern as an argument; the plain string would make such a loop match itself forever. The rake process's direct children (`tar`/`gzip`, `pg_dump`, `gitaly-backup`) get SIGTERM as well, rake first. With rake alone, the exception only fires once the in-flight pipeline returns, so the current target is dumped to the end anyway. The wait is for exit, not completion, capped by `STOP_TIMEOUT`. The SIGTERM and the wait run as a single in-container `sh -c`, which exits 124 on timeout so that a timeout stays distinguishable from a failed `docker exec`; polling with one `docker exec` per check would cost up to 150 round-trips. Past the timeout it prints the PID and a `pgrep` command to watch, and still releases the holds. Signals are deferred during the wait, because a second Ctrl+C exiting inside the EXIT trap would skip the release entirely.

Measured on a disposable 19.2.6 EE container with a 3GB file in uploads, interrupting during `Dumping uploads`:

| SIGTERM sent to | exit after | next target started? | cleanup |
|---|---|---|---|
| rake only | 43s (after the uploads `tar \| gzip` finished) | no | staging, `backups/tmp`, PID file all removed; no processes left |
| rake, then its children | 1s | no — the pending `SignalException` wins over the target's failure path | same |

The risk the second row rules out: that a killed `tar` would surface as a `FileBackupError`, which `run_create_task` rescues, and let the run continue to the next target.

The progress bar's `_size_poller` had the same orphan problem in its own right. Its in-container `while true` loop outlives the local `docker exec` client that `_stop_size_poller` and `_handle_signal` kill. On a run that goes on to upgrade, the container swap removed it; after a cancel or an aborted backup it kept polling every 0.5s until the container restarted (found by the 19.2.6 E2E). The loop now ends itself: once the backup process has been seen and is gone, or after ~10 minutes if it never appears. It takes `_BACKUP_PROC_PATTERN` as a positional argument, which is exactly the self-match case the bracket form exists for.

### Container Recreate

Each hop used to recreate the container with `docker run $LOG_ARGS $VOLUMES $PORTS`, so everything else silently vanished on the first upgrade (#22): `GITLAB_OMNIBUS_CONFIG` and other env, `--shm-size` (back to 64MB), the port bind IP (a `127.0.0.1` port reopened on `0.0.0.0`/`[::]`), user-defined networks, hostname, labels. In the 19.3.3 → 19.4.1 E2E that found it, the lost `puma['worker_processes'] = 0` let 32 workers fill the 64MB `/dev/shm`, Sidekiq died with `machine stack overflow in critical region`, and `wait_for_background_migrations` never returned.

The fix copies the configuration wholesale instead of picking flags: `docker container inspect` → jq (`_CONTAINER_SPEC_JQ`) → `POST /containers/create`. The CLI has no "create from inspect" command, and the create body has the same shape as inspect's `Config`/`HostConfig`, so nothing has to be translated field by field. `CONTAINER_SPEC` is built once, before the backup, and reused by every hop: the image comparison below needs the image the original container was created from, and the first hop deletes it.

What must not be copied verbatim:
- `Env`, `Labels`: mixed with what the image put in. Entries equal to the old image's are dropped, or the old `PATH`, or a derived image's `org.upgrade-gitlab.base`, would be pinned onto the new image.
- Every other key of the old image's `Config` (`Cmd`, `Entrypoint`, `Healthcheck`, …): dropped when equal to the old image's (empty values normalized — the container has `User: ""` where the image has `null`), so the new image's defaults apply. The keys come from the image rather than a fixed list, so a field Docker adds later is not silently pinned; newer daemons omit empty keys from the image config, and the container's matching empty values then stay in the request, where they mean "image default" anyway. `ExposedPorts` is kept, because `-p` adds to it.
- `Hostname`: dropped when it is the container ID prefix (Docker's default).
- Anonymous volumes appear only in `.Mounts`, not in `HostConfig.Binds`/`Mounts`; without them the new container would get a fresh empty volume. They are appended to `Binds` by name. Named volumes stay named (the old code turned them into host-path binds).
- `HostConfig.Links`: inspect returns `/target:/self/alias`, create wants `target:alias`.
- `ShmSize` is raised to 256MB (GitLab's recommendation) when smaller and IPC is private/shareable; a larger value is kept. Applies at the first recreate, so an instance only gets it on its next actual hop.
- Networks: API < 1.44 accepts one network at create (Synology DSM 7.2 ships Docker 24.0.2, API 1.43). The `NetworkMode` network goes into `NetworkingConfig`; the rest are attached with `POST /networks/{name}/connect` before start. Docker-added aliases (container ID prefix, container name) are removed.
- `LogConfig`: overwritten only for the `db` replacement and `UPGRADE_GITLAB_LOG_DRIVER` (see Container Log Driver).
- `RestartPolicy` is forced to `no`: a new version that dies with a FATAL error in reconfigure or a migration would otherwise be rebooted in a loop by `always`/`unless-stopped`. The original (`auto_restart_enabled`, `on-failure:N` retry count included) is restored by `_restore_restart_policy`, the third half of `_release_upgrade_holds`, so it is released wherever the other holds are: after post-upgrade verification on a normal end, an interrupt or an image-prep failure (the old code restored it only on full success, leaving interrupted runs at `no`). A FATAL exit inside the critical zone, or a `--ready-timeout` stop, skips the release, which deliberately leaves `no`. The next run then reads `no` as the original, so the policy has to be set back by hand after such a failure (#30 adds a state file).

The replacement is created as `<name>-upgrade-next` inside `_prepare_run_image`, while the old container still runs: create does not bind ports, and a rejected create then fails like a failed pull (`_image_prep_failed`, old version still up). The swap itself is `_swap_container`, run by every hop (the edition switch included): stop → rm → `docker rename` → `docker start` → readiness waits. If the replacement cannot be started there, the original is already gone, so it ends like a FATAL (`exit 1`, holds kept) instead of entering a readiness wait that could never succeed. A created-but-unused replacement is removed by the EXIT trap, but only while the original container still exists — if the rename failed after the rm, it is the only container left. A leftover from a killed run is removed (never forced) before the next create. `_docker_api` runs curl through `_run_isolated`: a Ctrl+C in the critical zone would otherwise kill only the client, reporting the interrupt as a failed create while dockerd may already have created the container. `_run_isolated` captures stderr itself into `_exec_err` instead of taking a path: `_docker_api` once passed `/dev/stderr`, which under `> log 2>&1` reopened the log file with O_TRUNC and erased everything logged before the container create.

Endpoint: `docker context inspect` gives the socket (it honours both `DOCKER_HOST` and contexts); `docker version` gives the API version. Both are checked with `_ping` right after the daemon probe, before anything else runs, and a non-`unix://` endpoint is refused there. On DSM the socket is `root:root 660` and users commonly alias `docker='sudo docker'`; the alias does not apply inside the script, so the existing daemon probe already implies root and curl can open the socket. DSM ships jq 1.5, which parses `A + B as $x` as `A + (B as $x | …)` (jq 1.7+ binds the whole sum), so every `as` in the jq program has its left side parenthesized.

### Container Log Driver
The container is recreated on every hop, so log settings must be passed explicitly or they silently revert to the daemon default. The copied `HostConfig.LogConfig` preserves the driver and its options (see Container Recreate), with one deliberate exception: Synology ContainerManager's proprietary `db` driver is replaced with `json-file` (`max-size=50m`, `max-file=3`).

`db` deadlocks dockerd whenever a container is stopped while `docker logs --follow` is attached — which is exactly what the non-CI stop path does. Confirmed by goroutine dump (`kill -USR1 <dockerd>`): `dblog.readLogs` → `logdb.tail` blocks on the logdb mutex; the stalled reader still holds the broadcaster mutex that `handleContainerExit` → `CloseStreams` → `broadcaster.Clean` needs; `handleContainerExit` holds the container State lock, so `ContainerStop` → `Daemon.Kill` → `State.GetPID`, `docker kill`, and `docker inspect` all block forever. containerd delivers the exit event correctly — the deadlock is entirely inside dockerd, which is why killing the shim does nothing and only a daemon restart recovers. `json-file` never enters `pkg/logdb`, making the deadlock structurally impossible.

Reproduces only under log-DB contention (a busy multi-container host with accumulated log history); a quiet 2-container host runs the identical code without wedging. `UPGRADE_GITLAB_LOG_DRIVER` overrides the choice in both directions. Trade-off: json-file logs do not appear in the DSM Container Manager UI (`docker logs` is unaffected).

### Reconfigure Deprecation Summary

Chef's trailing `Deprecations:` block from `gitlab-ctl reconfigure` was always streamed to stdout — `run_with_bouncing_bar` prints every new line of the command's output as it appears. It was simply unreadable: one reconfigure emits hundreds to thousands of lines, and reconfigure runs once per hop, so the block scrolls out of the buffer and repeats. Those warnings are the advance notice for the next major's hard abort (`print_stacktrace_errors`' "Removed configurations found" branch), so they are worth surfacing where they can be read.

`_record_deprecations` collects the block per hop; `print_deprecation_summary` re-prints the unique entries after `exit_critical`, tagged with the version each was first seen at. It sits before the interrupt branch, so an interrupted run still reports what it saw and still fires the accompanying `WARN` webhook (count plus the first three entries). The webhook stays at the call site rather than inside the function — a `print_*` function that also sends network notifications would be misnamed. `print_stacktrace_errors`' "Removed configurations found" branch prints the summary too: the keys that abort reconfigure are usually the ones earlier hops already warned about, so the collected list doubles as the "which key do I delete" shortlist.

The streaming loop is deliberately untouched. `run_with_bouncing_bar` draws its bar to `$_tty` and writes the command's output to stdout, so the call site just pipes through `tee` to keep one copy. The command-substitution idiom used by `check_secrets_integrity` and `check_migration_status` (`output=$(run_with_bouncing_bar ...)`) would also capture it, but suppresses the live stream — which is precisely what must be preserved here.

Two sources feed it. The pre-swap reconfigure in `check_gitlab_server_healthy 0` runs on the version about to be replaced, so on its own it never sees the target version: the last hop and the recovery path only call `check_gitlab_server_healthy 1`, which skips reconfigure, and the warnings of the version a run ends on (the starting point of the next upgrade, the ones that matter most) were missing from the summary (#29). A real case: `gitlab_exporter['server_name']` says "deprecated since 19.3", but it is only in the 19.4.1 deprecation list, not in 19.3.3's; a 19.3.3 -> 19.4.1 run reports it only through the new container's boot log, as `[19.4.1-ce.0]`. `_record_boot_deprecations` adds the second source without another reconfigure: the image's `/assets/init-container` runs `gitlab-ctl reconfigure` on every start, and its output is in `docker logs`. After `wait_for_ready`, which waits for that reconfigure to finish, `_swap_container` reads the new container's log; the recovery path reads the running one's. Both tag entries with `CNT_VERSION`, falling back to `CURRENT_VERSION` like the pre-swap collection: `_swap_container` sets `CNT_VERSION` to the new version as soon as the replacement has started, rather than at the end of the loop iteration, so everything after the swap reads the running version from that one variable instead of parsing it out of the image name. The pre-swap source stays: it is the only one that covers the starting version (a long-running container's boot log may be rotated away, and reflects the configuration it booted with), and the only one at all under `GITLAB_SKIP_RECONFIGURE`; from the second hop on it repeats what the previous boot log gave, which first-seen de-duplication absorbs. The log is read from `State.StartedAt` on, so a long-running container's earlier boots are not re-read. A warning the pre-swap reconfigure already saw keeps its first-seen version. With `GITLAB_SKIP_RECONFIGURE` there is no block, and nothing happens.

Block boundaries: the header is a line that is exactly `Deprecations:`; entries run until a blank line or the next top-level Chef section (`Running handlers`, `Chef Infra Client`, `gitlab Reconfigured!`). Deprecation text never ends in a colon, so it cannot be mistaken for the header. Parse failures are silent no-ops — a missed summary must never abort an upgrade. Associative-array subscripts are quoted throughout because the entries routinely contain `]` (`nginx['listen_port'] has been deprecated.`).

### TTY-Aware Output
Terminal detected → animated spinners, progress bars with ETA. No terminal (CI) → plain text status.

### HTTP Readiness and Ready Waits
`wait_for_ready` is the one readiness wait, used after every swap, after a `docker start` of a stopped container, and by the recovery path. Its condition (`_ready_check`) is: the Docker health status is `healthy`, or `none` when the image defines no HEALTHCHECK (`.State.Health` absent, e.g. a derived image with `HEALTHCHECK NONE`); the reconfigure the image runs at start has finished (`_boot_reconfigure_running`, `pgrep -f '[g]itlab-ctl reconfigure'` inside the container); and `/users/sign_in` answers 200 from inside the container (`_http_ready_check`). The reconfigure condition came with #29: services answer while that reconfigure is still running (on 19.4.1 the sign-in page was 200 six seconds before it finished), and its end restarts them once more and prints the `Deprecations:` block. Without it, the migration wait right after the swap and the next hop's pre-swap reconfigure could overlap that last restart, and the boot log read for deprecations was incomplete. The pattern is bracketed like `_BACKUP_PROC_PATTERN`; `gitlab-ctl` is the process to watch, not `cinc-client`, since omnibus-ctl prints the block after cinc-client exits. With `GITLAB_SKIP_RECONFIGURE` there is no such process. The HTTP check and the health check used to be two waits run back to back, so `--ready-timeout` applied twice per container and the `docker start` paths, which ran only the health wait, did not wait at all on an image without a HEALTHCHECK. The address comes from `/opt/gitlab/etc/gitlab-healthcheck-rc`, the file the image's own HEALTHCHECK (`gitlab-healthcheck`) sources: omnibus renders it at reconfigure with nginx's real listen port, scheme and relative URL (`url='http://localhost:18080/help'`, `flags=(--insecure)` as a bash array), and the check swaps `/help` for `/users/sign_in` (`_HTTP_READY_SH`). It used to be a fixed `http://localhost/users/sign_in`, which never answers when `external_url` carries a port, uses https (80 only redirects) or a relative path (#24); it surfaced once #22 stopped dropping `GITLAB_OMNIBUS_CONFIG`, which had been sending nginx back to port 80. The rc is not in the image, so a new container has none until its first reconfigure; until then, and on versions that never render it, the old address is used.

This used to be the CI-only path; outside CI the host curled `--target-url`. That flag is removed (#25) and now fails like `--source`: a user-given URL can point at another server (another GitLab on the host, a proxy that answers a maintenance page with 200) and pass for this container, or never answer at all. Filling it from `external_url` would not help either: the value may live only in `GITLAB_OMNIBUS_CONFIG`, a NAS without NAT loopback cannot reach its own public name, and a proxy still stands in for the container. The already-satisfied path uses the same in-container check.

`poll_with_bouncing_bar`, behind the wait, used to loop until its condition held, with only the ~1s death check (`print_stacktrace_errors`) as a way out. Inside the critical zone that meant a silent, signal-proof hang whenever the container was alive but the condition could never hold (45+ minutes in the #24 E2E, ended only by SIGKILL). What now ends it:
- `--ready-timeout` (default 3600s, `0` = no limit). Docker images run reconfigure and migrations while booting, so a major hop on a large instance can legitimately take tens of minutes. On timeout an interactive run asks whether to wait another round (default wait); `-y` stops via `_ready_timeout_fatal`: last 50 log lines, FATAL banner, ERR webhook, `exit 1`. It keeps the holds exactly like a FATAL, since the server's state is unknown: inside the critical zone the EXIT trap leaves them, and the runner and maintenance state files let a later run release them (the already-satisfied path does, once the in-container check passes). The restart policy has no state file and stays `no` (#30). The banner and these notes come from `_fatal_banner_keep_holds`, shared with the other FATAL exits that keep holds (a dead container in `print_stacktrace_errors`, a replacement that cannot start in `_swap_container`), so all three tell the user what is left behind and how to release it. The stuck-migration FATALs keep their own `_print_fatal_banner`.
- `print_stacktrace_errors` treats a container that is not running as dead, whatever its exit code. It used to look at `ExitCode` alone, so a container stopped with code 0 during the wait passed the check forever. A running container's exit code is reset to 0 at start.
- The condition runs every ~1s, with the death check, not on every 0.2s bar frame: it is a `docker exec` into a container that is busy booting, and outside CI it used to be a host curl.

A deferred Ctrl+C does not break the wait: once the swap has started the new container, leaving the wait would run post-upgrade verification against a server that is not up. The poll prints once that the run stops when the container is ready, bounded by `--ready-timeout`, and that Ctrl+\\ exits at once.

Known gap, outside these waits: the swap's own docker clients (`docker stop` under `run_with_bouncing_bar`, `docker rename`, `docker start`) are not isolated from the terminal's process group the way `_run_isolated` isolates its commands. The docker CLI (Go) re-enables SIGINT, so a terminal Ctrl+C in that window kills the client, and a killed `docker start` ends as "could not start the replacement container" (FATAL) (#31). Tests therefore signal the script pid alone, never through `timeout`, which signals the whole group.

- `tests/full_flow.bats` — Integration tests simulating full upgrade loops via mocks (includes stuck-migration scenarios)

### Integration Testing Against a Disposable GitLab (local Docker)

There is no integration job in CI (see CI Pipeline below). Anything the mocks cannot prove — how GitLab itself reacts to a signal, a lock, a real exit code, real cleanup — is verified by starting a throwaway GitLab in Docker on the work machine and running the real script against it. Needs about 4-5GB of RAM; a fresh container turned healthy in ~70s on a 32-core workstation.

```bash
docker run -d --name ugtest-gitlab --shm-size 256m \
  -p 127.0.0.1:18080:18080 \
  -v ugtest-gitlab-config:/etc/gitlab \
  -v ugtest-gitlab-logs:/var/log/gitlab \
  -v ugtest-gitlab-data:/var/opt/gitlab \
  -e GITLAB_OMNIBUS_CONFIG="external_url 'http://localhost:18080'; puma['worker_processes'] = 0; sidekiq['concurrency'] = 5; prometheus_monitoring['enable'] = false; gitlab_rails['backup_path'] = '/var/opt/gitlab/backups'" \
  gitlab/gitlab-ee:19.2.6-ee.0

# run the script against it (CI=true lifts -y's DISCORD_URL requirement)
CI=true ./upgrade-gitlab -y --no-step-limit

# cleanup; volumes too, since they cannot be reused at an older version
docker rm -f ugtest-gitlab && docker volume rm ugtest-gitlab-config ugtest-gitlab-logs ugtest-gitlab-data
```

Things that bit when this was first done:

- **An uninterrupted run really upgrades the container.** Once a run crosses a hop, the volumes hold a newer schema and cannot go back; to test at the old version again, remove the container *and* the volumes and start over. The script also deletes the previous image after a hop, so expect a re-pull.
- **Only one `gitlab/gitlab-ce|ee` container may exist on the host**, because the script auto-detects its target by image.
- **Make the backup slow enough to interrupt.** An empty instance backs up in seconds. A 3GB random file in uploads stretches the uploads stage to ~45s: `docker exec ugtest-gitlab sh -c 'dd if=/dev/urandom of=/var/opt/gitlab/gitlab-rails/uploads/big.bin bs=1M count=3000 && chown git:git /var/opt/gitlab/gitlab-rails/uploads/big.bin'`. Poll for `pgrep -f 'directory=/var/opt/gitlab/gitlab-rails/uploads'` inside the container to know when the dump is running.
- **A real Ctrl+C needs a real terminal, in the foreground.** Drive the script through `script(1)` and write `\003` into its stdin: the pty line discipline turns that into SIGINT for the foreground process group, exactly like a keypress. Keep `script(1)` in the foreground of a pipeline (`{ wait; printf '\003'; ... } | env --default-signal=INT script -q -e -f -c "..." log`) and never background it with `&`. A background job of a non-interactive shell starts with SIGINT ignored (`SigIgn: 0x6` in `/proc/<pid>/status`), and bash cannot trap a signal that was ignored on entry. The script then never sees ^C, while the docker client, whose Go runtime re-enables SIGINT, dies alone. In that state the first attempt carried on and upgraded the test container instead of cancelling. `env --default-signal=INT` makes the driver immune to how it was itself launched.

- **"healthy" is not "ready".** After the Docker health check turns healthy, the services were seen restarting once more (puma, workhorse and nginx all under a minute old), and requests returned 502 or were refused for tens of seconds. That restart is the end of the start-up reconfigure, which `wait_for_ready` now waits for. Poll `docker exec ugtest-gitlab curl -s -o /dev/null -w '%{http_code}' http://localhost:18080/-/readiness` until it returns 200 before driving the API or the script.
- **nginx listens on the `external_url` port.** With `external_url 'http://localhost:18080'`, nginx inside the container binds 18080, not 80, so `-p 127.0.0.1:18080:80` leads nowhere (curl exit 52, empty reply). Either map `18080:18080`, or do what the runner E2E did: call the API from inside the container (`docker exec ugtest-gitlab curl http://localhost:18080/api/v4/...`) and point the runner at `http://ugtest-gitlab:18080`.

**Running-jobs checks need a real runner.** A root PAT comes from `gitlab-rails runner` (`User.find_by_username("root").personal_access_tokens.create!(name:, scopes: [:api, :create_runner], expires_at:)`, then `puts t.token`). An instance runner comes from `POST /user/runners` (`runner_type=instance_type`, `run_untagged=true`). Put `gitlab/gitlab-runner` on a user-defined network shared with the GitLab container, and use the shell executor (`gitlab-runner register --non-interactive --url http://ugtest-gitlab:18080 --token glrt-... --executor shell`, then `gitlab-runner run`). A project whose `.gitlab-ci.yml` has one job with `GIT_STRATEGY: none` and `sleep N` gives a job that runs without needing a clone URL that resolves from the runner.

Scenarios verified this way on 19.2.6 EE (unlicensed: maintenance mode reports `unavailable`):

- Ctrl+C during the uploads dump: exit 130, the in-container backup stopped in ~1s, staging and PID file removed, no processes left, no upgrade.
- A backup already running (holding the 16.0+ lock) when the script starts: the script's backup fails with `Backup and restore in progress`, the run aborts with exit 1 and no upgrade, and the other backup is left alone to finish with `exit=0`.
- An uninterrupted run: a full 19.2.6 → 19.4.0 upgrade succeeded.
- A CI job running with `--running-jobs=abort`: the job is listed, the runner is paused, the run aborts with exit 1, the runner is resumed, and the job keeps running untouched.
- A CI job running with the default wait: while waiting, the runner showed `active=false` and the job `running`. **A paused runner finishes the job it already has**, which is what makes waiting meaningful. The job ended `success`, the script reported `All running CI jobs have finished.` and went on to the backup. The psql runner pause/resume works on 19.2.6 as well.

## CI Pipeline (.gitlab-ci.yml)

Stages: `lint` → `test` → `promote`

- **shellcheck**: Lints on develop, master, MRs
- **logic-test**: Runs `bats tests/` with kcov coverage on develop, master, MRs
- **promote-to-master**: Auto-pushes develop → master (canonical project only, uses `PUSH_TOKEN`)

There is no integration job. One existed — a real GitLab container upgraded end to end, then `batched_background_migrations` rows rewritten to status=4/5 to check stuck detection against a real PostgreSQL — but it had been failing continuously and was removed. Reviving it needs a privileged runner (it drove `docker:dind`) and a runner `maximum_timeout` above the default hour; a multi-hop upgrade of a real instance exceeds that. Real-GitLab verification is done locally instead — see "Integration Testing Against a Disposable GitLab" under Testing.

It also could not cross GitLab 19.0, which is worth knowing independently of CI: 19.0 dropped bundled Mattermost and its reconfigure hard-aborts with `Removed configurations found in gitlab.rb. Aborting reconfigure` when a `mattermost` key is present. On a stock install it *is* present — 18.x auto-generates a mattermost section in `gitlab-secrets.json` (salts, `sql_at_rest_encrypt_key`) even when Mattermost is unused, and regenerates it on every reconfigure, so each intermediate 18.x hop re-adds it. Crossing 19.0 cleanly would require editing secrets automatically, which is unsafe for real Mattermost users. This is an upstream GitLab issue, not a tool bug; users hit it as actionable output from `print_stacktrace_errors`' "Removed configurations found" branch (covered by a bats test).
